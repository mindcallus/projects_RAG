# thought_tracker 笔记记录应用项目说明

## 项目背景

thought_tracker 是一个围绕“想法记录与重新发现”设计的笔记应用。传统日记或笔记工具通常更擅长保存内容，但对个人思考场景存在几个明显问题：

- 内容容易按时间线堆积，旧笔记很快被淹没。
- 检索往往依赖用户自己记得关键词，回看效率不高。
- 工具更偏“存档”，而不是“重新组织、重新触发思考”。

这个项目的目标不是做一个功能很重的知识管理系统，而是做一个更轻量的个人思考容器：一方面保证记录过程足够顺手，另一方面通过随机重排、旧内容打捞和关键词高亮，让笔记不只停留在“写完即沉底”的状态。

## 核心功能

当前代码已经实现的核心能力可以概括为 8 类：

1. 用户注册、登录、JWT 鉴权与个人数据隔离。
2. 笔记创建、查询、更新、删除，支持分页与关键词搜索。
3. 标签创建、编辑、删除与按标签筛选。
4. 富文本编辑：写作页使用 Tiptap，支持粗体、斜体、文本颜色、高亮和字号调整。
5. 附件上传：支持先上传附件，再关联到具体笔记。
6. 随机重排浏览：展示页支持基于 LLM 的语义重排，也提供即时回退顺序。
7. 旧内容打捞：`excavate` 模块按时间与访问频次加权，随机挖出较久未看的笔记。
8. 关键词提取与高亮：对单条笔记调用大模型抽取关键词，并在详情弹窗中高亮显示。

补充说明：

- 富文本能力真实存在于输入侧；当前阅读侧主要将内容还原为纯文本/Markdown 形式展示，富文本样式保真度还有继续完善空间。
- “随机浏览”不是完全无规则洗牌，而是混合了 LLM 重排、缓存、回退策略和访问统计。

## 技术架构

### 前端

- React 18 + TypeScript
- Vite
- Tailwind CSS
- TanStack React Query
- React Router
- Tiptap 富文本编辑器
- Framer Motion 用于展示动效

前端主要页面包括登录、注册、写作页、展示页、日历页。写作页负责内容输入与附件、标签管理；展示页负责随机浏览、旧内容打捞、关键词高亮和详情查看。

### 后端

- FastAPI
- SQLAlchemy 2.0
- Pydantic 2
- JWT 鉴权

后端将接口统一挂载在 `/api` 下，当前包含认证、用户、笔记、标签、上传、随机重排、旧内容打捞等接口模块。

### 数据库

- SQLite

当前主要数据模型包括：

- `users`
- `thoughts`
- `tags`
- `thought_tags`
- `attachments`

其中 `thoughts` 表除正文、创建时间外，还缓存了 AI 提取的 `keywords`、更新时间、访问次数、最近浮出时间和浮出次数，用于支持关键词高亮与记忆考古。

### AI 接入

- Python `openai` SDK
- 通过 `base_url` 方式接入 DeepSeek 的 OpenAI 兼容接口
- 相关配置通过 `.env` 中的 `LLM_*` 变量管理

当前 AI 能力不是独立聊天助手，而是更贴近笔记场景的轻量增强：

- 笔记语义重排
- 语义相关卡片聚类
- 单条笔记关键词提取

### 测试与代码质量

- pytest
- FastAPI TestClient
- httpx
- ruff
- mypy
- 前端使用 TypeScript、ESLint

仓库内目前有 36 条后端测试用例，覆盖认证、用户、标签、笔记四类基础接口。

### 部署方式

- Dockerfile
- docker-compose
- 本地一键启动脚本 `start_app.sh`

当前 `docker-compose.yml` 主要覆盖后端服务与 SQLite 数据卷；前端仍以本地 Vite 开发方式启动，通过 `VITE_API_URL` 指向后端。

## AI 功能设计

### 1. LLM 驱动的笔记重排

目标不是做搜索，而是把同一批笔记重新排列成更适合阅读和联想的顺序。

输入：

- 当前用户的笔记列表
- 每条笔记的 `id`
- 内容预览
- 创建时间

处理方式：

- 后端先读取用户全部笔记。
- 当笔记较多时，不直接把全文都送给模型，而是采用“近期笔记 + 随机抽样”的混合采样。
- 将每条笔记压缩为 `id + preview + created` 的轻量结构后发送给模型。
- 提示词要求模型只返回 JSON，例如 `{"order": [3, 8, 1, 5]}`。
- 如果模型未配置、返回异常或结果无效，则回退为普通随机顺序。

输出：

- 笔记 ID 的新顺序

前端使用方式：

- 首屏先请求 `/api/shuffle/instant`，优先展示缓存结果或时间倒序结果，保证页面秒开。
- 如果没有缓存，再后台请求 `/api/shuffle/` 获取 LLM 重排结果，并无感更新页面。

工程取舍：

- 这套方案成本比“每次全量分析全部内容”更低。
- 由于目前还是 prompt 驱动重排，而不是向量检索或 embedding 排序，所以更适合“浏览体验增强”，还不等同于完整的 RAG 检索链路。

### 2. 语义聚类 Wallet

当笔记数量达到一定规模时，后端会额外尝试找出 2-4 条语义接近的笔记，返回如 `{"ids": [...], "theme": "..."}` 的结构。

当前实现特点：

- 只有在笔记数不少于 15 条时才会触发。
- 结果出现带有概率控制，不会每次都展示。
- 前端将这些笔记渲染为 Wallet 卡片堆栈，用于强化“局部主题被重新浮现”的体验。

这个能力本质上是一种轻量推荐：它不是直接给出“你应该看什么”，而是把语义相关的旧内容聚在一起。

### 3. 关键词提取与高亮

这是当前最清晰、最容易复用于 RAG 语料处理思路的一段 AI 链路。

输入：

- 单条笔记全文

后端处理：

- 调用 `llm_service.extract_keywords`。
- 提示词要求模型从文本中提取 3-5 个核心关键词或短语。
- 输出必须是 JSON，例如 `{"keywords": ["项目延期", "沮丧", "会议沟通"]}`。
- 结果写回 `thoughts.keywords`，并记录 `keywords_updated_at`，默认缓存 24 小时，避免重复调用模型。

前端处理：

- 详情弹窗打开时，请求 `/api/thoughts/{id}/keywords`。
- 将笔记内容转为纯文本后，用正则对关键词逐个匹配。
- 关键词以逐步显现的方式高亮展示，帮助用户快速看到一条笔记的语义重心。

当前关键词的用途：

- 已实现：高亮展示、辅助回看。
- 尚未实现：基于关键词的自动标签推荐、基于关键词的相关推荐。

也就是说，当前项目里的“推荐”主要体现在语义重排和聚类，而不是标签自动推荐。

### 4. 旧内容打捞（非 LLM，但与 AI 功能互补）

`excavate` 功能不是大模型驱动，而是通过规则算法让旧笔记更容易被重新看见。

主要规则：

- 笔记越旧，权重越高。
- 被访问次数越少，权重越高。
- 根据埋藏天数生成 `COMMON / VINTAGE / ANCIENT / ARTIFACT` 等稀有度标签。

这部分和 AI 重排一起，构成了项目“不是只记录，而是帮助回看”的核心体验。

### 当前效果

- 已落地 8 类核心功能，覆盖鉴权、笔记管理、标签、附件、富文本输入、随机浏览、旧内容打捞、关键词高亮。

- 代码已托管到 GitHub：`https://github.com/mindcallus/thought_tracker`

### 测试与验证现状

- 仓库内已有 36 条 pytest 用例，主要覆盖后端基础接口。
- 当前环境执行 `python3 -m pytest -q` 失败，直接原因是缺少 `python-jose` 依赖。
- 从现有代码看，测试文件中请求路径仍以旧版无 `/api` 前缀写法为主，和当前后端统一加 `/api` 前缀的实现存在待同步项。
- 当前执行 `npm run build` 失败，报错集中在 TypeScript/Vite 配置与若干未使用变量。
- 当前执行 `npm run lint` 失败，原因是 ESLint 配置依赖 `typescript-eslint` 包未正确加载。
- 当前未做正式用户测试。

### 现阶段限制

- AI 能力以 prompt 调用为主，尚未引入 embedding、向量数据库和完整 RAG 检索链路。
- 展示层对富文本样式的还原还不完整，当前更偏“保留内容本身”，而非严格保留编辑态样式。
- Docker Compose 主要覆盖后端，前端正式部署链路还没有完全收口。
- 日历页已有基础页面，但更多是界面占位，尚未打通按日期回看笔记的完整查询逻辑。

## 面试 STAR 表达

### S：背景（Situation）

我想做一个更适合个人思考记录的笔记应用。传统笔记工具更像是信息存档，写完以后内容通常按时间线沉底，后续回看很依赖手工搜索，旧笔记很难自然地再次进入思考流程。

### T：任务（Task）

我的目标不是做一个大而全的知识库，而是先做一个轻量可运行的产品原型：既能完成基础记录、标签和附件管理，又能通过 AI 或规则机制让旧内容被重新组织和再次触达。

### A：行动（Action）

- 我先用 FastAPI + SQLAlchemy 搭建了用户、笔记、标签、附件几类核心模型和接口。
- 在前端用 React + Tiptap 做了写作页，保证记录过程具备基础富文本能力。
- 为了解决“笔记写完就沉底”的问题，我做了两条增强链路：一条是基于时间和访问频次的 `excavate` 旧内容打捞；另一条是基于大模型的语义重排和语义聚类。
- 在 AI 接入上，我没有直接做复杂 Agent，而是先把输入输出收敛到稳定的 JSON 结构，例如关键词提取输出 `keywords`，重排输出 `order`，这样更容易落库、缓存和前端消费。
- 我还补了 pytest 测试夹具和 Docker 运行配置，方便后续继续扩展。

### R：结果（Result）

最终我做出了一个可运行的个人笔记原型，已经覆盖记录、管理、回看和轻量 AI 增强几个核心场景。当前项目代码已托管到 GitHub，仓库内有后端自动化测试用例，并完成了大模型关键词提取与语义重排的基础闭环。当前未做正式用户测试，前端构建和测试链路也还有待继续收口，但作为一个面向 AI 应用方向的项目样本，已经能较完整体现我在需求拆解、后端设计、数据建模、LLM 接入和工程落地上的能力。
